# 기능명세서 — 자녀 개인 일정(학원 등) 시간표 추가

> 상위 문서: [기능명세서.md](기능명세서.md) §4.9 시간표 (항목 8.3.1–8.4.1)
> 본 문서는 그 항목을 **구현 가능한 수준**으로 상세화한 것이다.
> 상태: 설계안(미구현). 먼저 로컬에서 검증 후 배포.

---

## 1. 문서 목적 / 범위

학부모가 **수업(시간표) 탭**에서 자녀의 **개인 일정(학원·피아노·태권도 등)을 직접 등록·수정·삭제**하고, 학교 시간표와 함께 한 화면에서 볼 수 있게 한다.

기존 [기능명세서.md](기능명세서.md)에는 이미 다음이 정의되어 있으나 **아직 구현되지 않았다.**

| 번호 | 기능 | 설명 |
| --- | --- | --- |
| 8.3.1 | 자녀 일정 생성 | 자녀별로 학원, 피아노, 태권도 등 반복 개인 시간을 등록할 수 있다. |
| 8.3.2 | 입력 항목 | 제목, 요일, 시작 시간, 종료 시간, 메모를 입력한다. |
| 8.3.3 | 수정/삭제 | 등록된 자녀 일정표를 수정하거나 삭제할 수 있다. |
| 8.4.1 | 학교 시간표와 통합 노출 | 학교 시간표와 자녀 일정표를 같은 흐름 안에서 함께 보여준다. |

본 문서는 위 8.3.2의 "요일/시작/종료 시간" 명세를 그대로 따른다 → **주간 반복(요일 기반) 모델**.

### v1 범위 (이번 작업)
- 수업 탭(`?tab=classes`)에 개인 일정 **추가/수정/삭제 + 통합 표시**
- 요일 기반 주간 반복 일정 (학원 = 매주 같은 요일·시간)
- 월~금 5일 뷰 (현재 시간표 뷰와 동일 범위)

### v1 제외 (향후 확장 — §16)
- 일회성(특정 날짜) 개인 일정 / 월간 캘린더(일정 탭) 표시
- 주말(토·일) 표시, 반복 예외(방학 제외), 알림, 개인 일정 번역, 색상 자유 선택(팔레트만 제공)

## 2. 핵심 결정 사항 (검토 요망)

명세를 확정하기 전 아래 결정이 전체 구현 방향을 좌우한다. **굵은 항목이 본 문서의 권장안**이다.

### 결정 ① 표시 방식 — 카드 뷰 확장 vs 시간표 그리드 전환
현재 `TimetableWeekView`는 **요일별 카드 + 교시(1교시·2교시…) 리스트**다. 첨부 스크린샷(에브리타임)은 **시간축 그리드**다. 두 방향이 있다:

- **(A) 권장 — 기존 카드 뷰 확장**: 각 요일 카드 하단에 "개인 일정" 구획을 추가해 `학원 · 15:30–16:30 · 위치`를 리스트로 표시. 기존 렌더링·번역 파이프라인 재사용, 변경 최소, 로컬 검증 빠름.
- (B) 시간표 그리드 전환: 전체를 시간축 그리드로 재구축. 스크린샷과 더 비슷하지만 학교 시간표가 교시 기반(절대 시각 없음)이라 정합이 어렵고 변경 규모가 큼. → 별도 과제로 분리 권장.

> ⚠️ 이 결정이 §9(UI)의 대부분을 좌우한다. 본 문서는 **(A)** 기준으로 작성. (B)를 원하면 §9를 다시 설계해야 함.

### 결정 ② 반복 모델 — 요일 기반(권장) vs 날짜 기반
학원은 "매주 화·목 4시"처럼 반복된다. 기존 명세 8.3.2도 "요일"을 입력 항목으로 못박았다. → **요일 기반(`day_of_week`) 채택.** 일회성 날짜 일정은 v2.

### 결정 ③ 시각 표현 — 절대 시각(권장) vs 교시 번호
학원은 "16:00"이지 "N교시"가 아니다. → 학교 시간표(교시)와 **별도 필드(start_time/end_time)** 로 저장하고, 카드에서 별도 구획으로 표시. (탐색 중 "교시 번호로 매핑" 안이 있었으나 의미가 왜곡되어 **기각**.)

### 결정 ④ 표시 범위 — 월~금(권장) vs 주말 포함
현재 뷰는 월~금 5일(`buildTimetableDays` `i<5`)이고 스크린샷도 월~금이다. → v1은 월~금. DB는 0–6 모두 허용(주말은 v2 노출).

## 3. 사용자 흐름

```text
캘린더 탭 → "수업" 탭 진입
  -> 학교 시간표(NEIS) + 개인 일정이 요일별로 함께 표시
  -> "+ 개인 일정 추가" 버튼
       -> 바텀시트: 제목 / 요일 / 시작·종료 시간 / 위치 / 메모 입력
       -> 저장 → 즉시 해당 요일 카드에 반영
  -> 기존 개인 일정 항목 탭 → 수정 / 삭제(확인 모달)
```

선택 자녀 기준(현재 페이지는 `children?.[0]`)으로 동작한다. 다자녀 전환은 기존 동작을 따른다.

## 4. 상세 기능 명세 (기존 §4.9 시간표 확장)

| 번호 | 기능 | 설명 |
| --- | --- | --- |
| 8.3.1 | 자녀 개인 일정 생성 | 선택 자녀에 대해 학원/피아노/태권도 등 **주간 반복** 개인 일정을 등록한다. |
| 8.3.2 | 입력 항목 | **제목(필수), 요일(필수, 월~금), 시작 시간(필수), 종료 시간(필수), 위치(선택), 메모(선택)**. 색상은 팔레트에서 선택(기본 파랑). |
| 8.3.3 | 입력 검증 | 제목 비어있지 않음, 시작<종료 시간. 위반 시 폼 하단에 안내(`role="alert"`). |
| 8.3.4 | 수정 | 기존 항목을 탭하면 동일 폼에 값이 채워진 상태로 열려 수정·저장한다. |
| 8.3.5 | 삭제 | 삭제 시 확인 모달("이 일정을 삭제할까요? 삭제하면 복구할 수 없어요.") 후 영구 삭제한다. |
| 8.3.6 | 소유권 | 본인 자녀의 일정만 생성/조회/수정/삭제할 수 있다(RLS + 서버 액션 교차검증). |
| 8.4.1 | 학교 시간표와 통합 노출 | 각 요일 카드에서 학교 시간표(교시) 아래에 "개인 일정" 구획으로 함께 표시한다. |
| 8.4.2 | 빈 상태 | 학교 시간표가 없어도 개인 일정만 있으면 표시한다. 둘 다 없으면 "수업 정보 없음". |
| 8.4.3 | 미지원 학교 처리 | 시간표 미지원(`timetableUnsupported`)이어도 개인 일정 추가·표시는 가능해야 한다. |

## 5. 데이터 모델

### 5.1 새 테이블 `child_personal_schedules`

기존 child 소유 리소스(notices·schedules)의 RLS·트리거 관례를 그대로 따른다.

**파일(신규): `supabase/migrations/0035_child_personal_schedules.sql`**

> ⚠️ 마이그레이션 번호 주의: 현재 `0030_`이 두 개(`..._add_translated_title`, `..._school_events_end_date`) 충돌해 있으나 순차 최대는 `0034`다. 새 파일은 **0035**로 한다.

```sql
-- 자녀 개인 일정(학원/피아노/태권도 등 주간 반복) 저장
create table if not exists public.child_personal_schedules (
  id uuid primary key default gen_random_uuid(),
  child_id uuid not null references public.children(id) on delete cascade,

  title text not null,
  -- 0=일 ~ 6=토 (JS getUTCDay() / calendar.weekdays 배열 인덱스와 동일)
  day_of_week smallint not null check (day_of_week between 0 and 6),
  start_time time not null,
  end_time time not null,
  location text,
  memo text,
  -- 팔레트 키(blue/green/orange/purple/pink). 자유 hex 미허용
  color text not null default 'blue',

  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  check (start_time < end_time)
);

create index if not exists child_personal_schedules_child_day_idx
  on public.child_personal_schedules (child_id, day_of_week);

-- updated_at 자동 갱신 (0001에서 정의된 공용 함수 재사용)
drop trigger if exists child_personal_schedules_set_updated_at on public.child_personal_schedules;
create trigger child_personal_schedules_set_updated_at
before update on public.child_personal_schedules
for each row execute function public.set_updated_at();

-- RLS: 본인 자녀의 일정만 (notices/schedules와 동일한 children-join 패턴)
alter table public.child_personal_schedules enable row level security;

do $$
begin
  if not exists (
    select 1 from pg_policies
    where schemaname = 'public'
      and tablename = 'child_personal_schedules'
      and policyname = 'child personal schedules manage own child'
  ) then
    create policy "child personal schedules manage own child"
    on public.child_personal_schedules for all
    using (
      exists (
        select 1 from public.children
        where children.id = child_personal_schedules.child_id
          and children.user_id = auth.uid()
      )
    )
    with check (
      exists (
        select 1 from public.children
        where children.id = child_personal_schedules.child_id
          and children.user_id = auth.uid()
      )
    );
  end if;
end;
$$;
```

설계 근거:
- **`child_id` FK + children-join RLS**: 별도 `user_id` 컬럼은 두지 않는다(중복·불일치 위험). 코드베이스의 notices/schedules/notice_cards가 모두 이 패턴.
- **`for all`**: school_events는 `for select`(시스템 생성)지만 개인 일정은 사용자가 CRUD하므로 `for all`.
- **`day_of_week` 정수(0–6)**: `calendar.weekdays`(일~토)·JS `getUTCDay()`와 동일 인덱스 → 매핑 코드 단순.
- **`color` 팔레트 키**: 테마 안정성을 위해 raw hex 대신 키로 저장, 컴포넌트에서 토큰 매핑.
- v1은 `valid_from/valid_until`·`is_active`(소프트삭제) **미포함**(향후 §16). 삭제는 확인 모달 + 물리 삭제.

## 6. 데이터 조회 / 주입 (`app/(app)/calendar/page.tsx`)

### 6.1 조회 위치
현재 흐름:
- L107–115: 자녀 조회 → `child = children?.[0]`, `child.id` 확보
- L217–243: NEIS 시간표 조회 → `buildTimetableDays(monday, periods)` → `translateTimetableDays(...)`

**개인 일정은 시간표 지원/미지원과 무관하게 항상 조회**해야 하므로(8.4.3), L217의 `if (!child?...)` 분기 **바깥**에서 한 번 조회한 뒤 두 분기 모두에 주입한다.

```ts
// child 확보 직후 (L115 근처)
let personalItems: PersonalScheduleItem[] = []
if (child?.id) {
  personalItems = await fetchPersonalSchedulesForChild(supabase, child.id)
}
```

`supabase`는 기존 변수(일반 사용자=서버 클라이언트(RLS), 테스트 바이패스=서비스 클라이언트)를 그대로 사용 → RLS가 본인 자녀로 자동 스코프.

### 6.2 주간 배치
`buildTimetableDays`(L306–323)가 만든 월~금 `TimetableDayEntry[]`에, 각 날짜의 요일(`getUTCDay`)과 `day_of_week`가 일치하는 개인 일정을 붙인다. `buildTimetableDays`에 인자를 추가하거나 별도 `attachPersonalItems(days, personalItems)`로 분리(권장: 단일 책임).

```ts
function attachPersonalItems(
  days: TimetableDayEntry[],
  items: PersonalScheduleItem[],
): TimetableDayEntry[] {
  return days.map(day => {
    const weekday = new Date(`${day.isoDate}T00:00:00Z`).getUTCDay()
    return {
      ...day,
      personalItems: items
        .filter(it => it.dayOfWeek === weekday)
        .sort((a, b) => a.startTime.localeCompare(b.startTime)),
    }
  })
}
```

> 개인 일정 제목은 **번역하지 않는다**(부모가 직접 입력한 표현). 따라서 `translateTimetableDays` 적용 **후** `attachPersonalItems`를 호출해 번역 경로에서 제외한다.

### 6.3 조회 헬퍼

**파일(신규): `lib/child-personal-schedules.ts`**

```ts
import type { SupabaseClient } from '@supabase/supabase-js'
import type { Database } from '@/types/database'
import { isTestEntryBypassEnabled, TEST_BYPASS_CHILD_ID } from '@/lib/test-entry-bypass'

export interface PersonalScheduleItem {

  memo: string | null

export async function fetchPersonalSchedulesForChild(
  client: SupabaseClient<Database>,
  childId: string,
): Promise<PersonalScheduleItem[]> {
  // 로컬 테스트 바이패스: 합성 자녀는 실제 DB row가 없으므로 목 데이터 (§11)
  if (isTestEntryBypassEnabled() && childId === TEST_BYPASS_CHILD_ID) {
    return mockPersonalSchedules()
  }
  const { data, error } = await client
    .from('child_personal_schedules')
    .select('id, title, day_of_week, start_time, end_time, location, memo, color')
    .eq('child_id', childId)
    .order('day_of_week')
    .order('start_time')
  if (error) throw error
  return (data ?? []).map(r => ({
    id: r.id,
    title: r.title,
    dayOfWeek: r.day_of_week,
    startTime: r.start_time.slice(0, 5),  // "HH:MM:SS" → "HH:MM"
    endTime: r.end_time.slice(0, 5),
    location: r.location,
    memo: r.memo,
    color: r.color,
  }))
}
```

## 7. 서버 액션 (CRUD)

프로젝트 표준은 **Server Action(`'use server'`)** + `useTransition` + `revalidatePath`다 (온보딩 `saveChildAndProfile`, 설정 `updateChildSchool`과 동일). API route는 쓰지 않는다.

**파일(신규): `app/(app)/calendar/actions.ts`**

```ts
'use server'

import { revalidatePath } from 'next/cache'
import { createSupabaseServerClient } from '@/lib/supabase/server'

interface SaveInput {
  childId: string
  title: string
  dayOfWeek: number
  startTime: string   // "HH:MM"
  endTime: string     // "HH:MM"
  location?: string
  memo?: string
  color?: string
}

async function assertOwnsChild(supabase, userId: string, childId: string) {
  const { data: child } = await supabase
    .from('children').select('id')
    .eq('id', childId).eq('user_id', userId).maybeSingle()
  if (!child) throw new Error('권한이 없어요.')
}

export async function createPersonalSchedule(input: SaveInput) {
  const supabase = await createSupabaseServerClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) throw new Error('로그인이 필요해요.')

  const title = input.title.trim()
  if (!title) throw new Error('일정 제목을 입력해 주세요.')
  if (input.startTime >= input.endTime) throw new Error('종료 시간이 시작 시간보다 빨라요.')
  if (!Number.isInteger(input.dayOfWeek) || input.dayOfWeek < 0 || input.dayOfWeek > 6)
    throw new Error('요일을 다시 선택해 주세요.')

  await assertOwnsChild(supabase, user.id, input.childId)

  const { error } = await supabase.from('child_personal_schedules').insert({
    child_id: input.childId,
    title,
    day_of_week: input.dayOfWeek,
    start_time: input.startTime,            // "HH:MM" → time 캐스팅 OK
    end_time: input.endTime,
    location: input.location?.trim() || null,
    memo: input.memo?.trim() || null,
    color: input.color || 'blue',
  })
  if (error) throw new Error('일정 저장에 실패했어요.')
  revalidatePath('/calendar')
}

export async function updatePersonalSchedule(input: SaveInput & { id: string }) { /* 동일 검증 + .update().eq('id', id), 소유권은 RLS가 보장 */ }

export async function deletePersonalSchedule(id: string) {
  const supabase = await createSupabaseServerClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) throw new Error('로그인이 필요해요.')
  const { error } = await supabase.from('child_personal_schedules').delete().eq('id', id)
  if (error) throw new Error('일정 삭제에 실패했어요.')
  revalidatePath('/calendar')
}
```

설계 노트:
- **RLS가 1차 방어선**(write 시 `with check`로 타 자녀 차단). create는 `child_id`를 직접 받으므로 `assertOwnsChild`로 명시 교차검증까지 한다(설정 액션이 `.eq('user_id', user.id)`를 명시하는 관례와 동일 취지).
- update/delete는 `id` 기반 — RLS `using`이 본인 자녀 행만 통과시키므로 안전. 방어적으로 한 번 더 select 확인해도 됨.
- 캐시: 캘린더 페이지는 동적(쿠키/auth) → **`revalidatePath('/calendar')`** 로 충분. 별도 `serverCacheTags` 신설 불필요(개인 일정 read는 `unstable_cache` 미사용).

## 11. 로컬 테스트 모드 대응 (중요)

사용자가 **"일단 로컬로 test"** 한다고 했으므로 두 경로를 모두 지원한다.

`lib/test-entry-bypass.ts`의 바이패스 모드는 합성 자녀(`id='test-entry-bypass-child'`)를 반환하며 **실제 `children` row가 없다.** → FK 때문에 `child_personal_schedules` INSERT 불가.

| 모드 | 읽기 | 쓰기(CRUD) |
| --- | --- | --- |
| **바이패스(`TEST_ENTRY_BYPASS=true`)** | `fetchPersonalSchedulesForChild`가 **목 데이터** 반환(§6.3) → UI/렌더 검증 가능 | 합성 자녀라 저장 불가 → 폼 제출 비활성 또는 "데모 모드" 안내 |
| **실제 로그인(권장 전체 검증)** | DB 조회(RLS) | 실제 CRUD 동작 → 8.3 전체 흐름 검증 |

목 데이터(예시): 화 16:00–17:00 "영어학원", 목 17:00–18:00 "태권도".

**CRUD까지 로컬에서 검증하려면**: 마이그레이션 0035를 로컬 Supabase에 적용 → 실제 계정 로그인 → 자녀 등록 상태에서 테스트. (바이패스 모드는 표시 전용 검증.)

> 운영 DB는 [migrations 수동 적용](기능명세서.md) 관례(대시보드 SQL Editor)를 따른다. 로컬은 `supabase db push` 또는 로컬 SQL 적용.
