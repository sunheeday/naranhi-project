# Agent Workflow

이 프로젝트의 모든 개발 요청은 두 개의 역할을 분리해서 처리한다.

실제 역할 프롬프트 파일:

- [Development Agent](../.agents/development-agent.md)
- [Verification Agent](../.agents/verification-agent.md)

## 목적

- 구현과 검증을 분리해서 자기확신성 실수를 줄인다.
- 변경 이유, 가정, 검증 범위를 매 요청마다 남긴다.
- 기능 추가, 버그 수정, 리팩터링 모두 같은 흐름으로 처리한다.

## Agent 1. Development Agent

개발 에이전트는 "만드는 역할"을 맡는다.

### 책임

- 요청의 목표와 범위를 정리한다.
- 기존 코드와 제약사항을 확인한다.
- 필요한 코드를 구현한다.
- 구현 중 생긴 가정과 결정 사항을 기록한다.
- 어떤 검증이 필요한지 검증 에이전트에 전달한다.

### 기본 액션

1. 요청을 한두 문장으로 재정의한다.
2. 영향받는 파일과 기능 범위를 파악한다.
3. 구현 계획을 세운다.
4. 코드를 수정한다.
5. 가능하면 로컬 검증을 먼저 실행한다.
6. 아래 항목을 검증 에이전트에 넘긴다.

### 인계 항목

- 무엇을 바꿨는지
- 왜 그렇게 바꿨는지
- 특히 조심해서 봐야 할 회귀 지점
- 실행한 테스트와 아직 못 한 테스트
- 남아 있는 가정, 제한사항, 미해결 리스크

## Agent 2. Verification Agent

검증 에이전트는 "의심하고 확인하는 역할"을 맡는다.

### 책임

- 요청이 실제로 충족되었는지 확인한다.
- 구현 누락, 회귀, 예외 케이스를 찾는다.
- 테스트 부족 여부를 지적한다.
- 필요하면 재현 절차와 수정 제안을 남긴다.
- 승인 가능 여부를 명확하게 판단한다.

### 기본 액션

1. 원래 요청과 구현 결과를 비교한다.
2. 변경 파일과 관련 흐름을 리뷰한다.
3. 버그 가능성이 높은 분기와 예외 케이스를 점검한다.
4. 테스트 커버리지와 수동 검증 범위를 평가한다.
5. 결과를 아래 상태 중 하나로 정리한다.

### 검증 결과 상태

- `approved`: 요구사항 충족, 치명적 이슈 없음
- `approved_with_risks`: 동작은 가능하지만 남은 리스크 있음
- `changes_requested`: 수정이 필요한 문제 발견

### 보고 형식

- Findings: 버그, 회귀, 누락, 위험 요소
- Test Gaps: 부족한 자동/수동 검증
- Verdict: `approved` / `approved_with_risks` / `changes_requested`

## 기본 운영 순서

모든 개발 요청은 아래 순서를 따른다.

1. Development Agent가 요구사항과 영향 범위를 분석한다.
2. Development Agent가 구현한다.
3. Development Agent가 자체 테스트를 수행하고 인계 메모를 남긴다.
4. Verification Agent가 독립적으로 리뷰하고 검증한다.
5. Findings가 있으면 Development Agent가 수정한다.
6. 필요하면 Verification Agent가 재검증한다.
7. 최종 응답에는 구현 내용과 검증 결과를 함께 남긴다.

## 요청 유형별 기준

### 기능 추가

- 정상 흐름뿐 아니라 실패 흐름도 검증한다.
- 번역, 권한, 상태 변화, 데이터 저장 여부를 같이 확인한다.

### 버그 수정

- 재현 경로를 먼저 정리한다.
- 수정 후 같은 버그가 다시 생길 수 있는 인접 경로를 함께 본다.

### 리팩터링

- 동작 불변성이 핵심이다.
- 공개 API, 데이터 shape, 사용자 메시지 변화 여부를 확인한다.

## 완료 조건

아래를 모두 만족해야 요청이 완료된 것으로 본다.

- 코드 변경이 요청 범위와 일치한다.
- 검증 에이전트 리뷰가 끝났다.
- 치명적 Findings가 없거나 해결되었다.
- 실행한 테스트와 남은 리스크가 최종 응답에 기록되었다.

## 이 레포에서의 실제 적용 규칙

- 앞으로 Codex는 개발 요청을 받으면 먼저 Development Agent 관점으로 구현을 진행한다.
- 구현 후에는 반드시 Verification Agent 관점으로 한 번 더 점검한다.
- 사용자가 명시적으로 "검증 없이 빠르게" 같은 예외를 요청하지 않는 한 이 절차를 기본값으로 유지한다.
- 코드 리뷰 요청이 들어오면 Verification Agent 역할을 우선한다.
